# 設計のポイント

## RULE, GOAL, DATA は一体で考える

- GOAL はソフトウェアの内容を決定します。

  まずはこれを記述しないと始まりません。

- RULE はソフトウェアのリスク対策です。

  どんな方法でも GOAL を達成可能なことはまずなく、満たすべき条件は明示する必要があります。

- DATA は依存関係の要です。

  GOAL が成立するために何をでき、RULE が何を許可/禁止するかを厳密に定義し、DATA がどの状態を取りうるかをコントロールすることが破綻しない設計のカギとなります。

## 人間が把握できるアーキテクチャを維持する

人間がアーキテクチャを把握できるように、RULE には設計原則を必ず記載します。

- 一般的な設計原則の例
  - 依存方向は一方向であること
  - 任意のユースケースで起きるソフトウェアの変更の影響範囲を予測し、説明可能であること
- 各々のソフトウェア固有の用語で記述する設計原則
  - 循環参照を起こさないための上位・安定コンポーネントの強制
  - ユースケースに応じてさらに、参照する範囲を狭める指定

## 変更に対する影響範囲を明確にできるアーキテクチャを維持する

開発者がソフトウェアに対して行うユースケースとしては、ソフトウェアの各コンポーネントへの変更があります。コンポーネントの変更で新たな依存関係が循環参照を起こすことは避ける必要があります。また変更を行ったコンポーネントは、その影響範囲をすべてテストする必要があります。際限なくソフトウェア全体を調査し、状況に応じて変更する、なども御免です。

破綻しない設計とは、変更に対する影響範囲が常に予測可能であることを意味します(と考えています)。
そのためには、影響範囲の閉包 (Impact Locality) が必要です。
どんな変更に対しても、影響範囲が閉じていて予測でき、説明可能であるアーキテクチャを維持する必要があります。

- 一般的な設計原則の例(変更時)
  - 依存関係は一方向のまま維持すること
  - 変更する場所は局所化されていること
  - 境界を超える変更は説明できること
  - 新機能追加時の変更箇所が予測できること
  - テスト範囲は変更箇所から導出できること
- 各々のソフトウェア固有の用語で記述する設計原則
  - 決定している境界を変更することを禁止するルールを記載
    (公開APIや型の維持, ディレクトリ構成など)
  - ユースケースごとに変更できるコンポーネントを指定するルールを記載
    (後述)

## 変更に対する規則を明示する

ソフトウェア変更のユースケースに対して、その変更がどの程度広範なコンポーネントに影響を及ぼすかどうかあらかじめ RULE にしておくことが考えられます。

これを実際に記述すると、変更に対して許可/禁止する内容を記述した一種の契約として現れます。

```
GOAL 新しいユーザーロールを追加し、既存の閲覧権限をそのロールに付与する
    RULE 変更可能なのはユーザー管理のみで、データ参照部その他は禁止
    RULE テスト可能なのはユーザー管理とデータ参照部のみで、その他は
        テスト不要のままとする
```

## GOAL, RULE の矛盾を検査する

GOAL と RULE を詳細化すると、どこかで矛盾が生じます。
場合によっては、可能なら守りたい目的や規則、というものも出てくるので、
これらは WANT として記述することも検討します。
